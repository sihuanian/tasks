# 费用报销单 · 需求文档（wi-t1000149）

- 文档版本：v1.0（初始需求基线）
- 需求来源：用户任务原话「创建费用报销单」
- 基线说明：当前工作区不包含费用报销相关的既有代码或已冻结需求，本基线为新增设计。文中明确标注「推荐基线 / 设计假设」的条目，是可以安全推导的产品规则，不是用户已确认的决定，用户可随时调整。
- 目标设备：桌面 Web（默认记录；用户未要求移动端或窄屏适配）。

## 1. 项目背景与目标

### 1.1 要解决的问题
报销经办人员需要一种在线方式创建费用报销单：填写报销基本信息和逐项费用明细，由系统完成金额汇总与合规校验后保存为草稿或正式提交，并能在之后随时查询已创建的单据。

### 1.2 服务对象
报销单的填写者（经办人）。用户未要求设计角色体系或权限方案，本需求基线不定义角色与权限矩阵，也不从功能或旅程推导权限规则。

### 1.3 成功结果
一名用户可以在系统中完成「新建 → 填写表头与费用明细 → 系统校验与自动合计 → 保存草稿 → 提交」的完整创建流程；创建后的报销单具备唯一单号与明确状态，可查询、可查看；保存的数据在页面刷新或重新打开后仍然可读。

## 2. 用户旅程与关键场景

### J1 新建并保存草稿
1. 用户打开费用报销单列表页，点击「新建报销单」入口。
2. 系统打开空白报销单填写界面，申请日期默认带出当天（推荐基线）。
3. 用户填写报销事由、报销人等必要信息，可先不填明细。
4. 关键决策点：选择「保存草稿」。系统校验必填项后保存，生成唯一报销单号，单据状态为「草稿」，并在列表中可见。
5. 系统反馈：保存成功提示与列表新纪录；必填项缺失或格式错误时给出可见的错误原因，不发生保存。

### J2 补全费用明细并提交
1. 用户在新建的草稿（或列表/详情页重新打开的草稿）上逐条添加费用明细（日期、类别、用途说明、金额）。
2. 系统实时计算合计报销金额，任何明细变更后合计立即同步（引用规则 C2）。
3. 关键决策点：选择「提交」。系统执行提交级校验（引用规则 C5）。
4. 系统反馈：校验通过后单据状态变为「已提交」，转为只读；校验不通过时停留在可编辑状态并给出具体原因。

### J3 查询与查看已创建的报销单
1. 用户在列表页浏览报销单，可按状态、关键字（报销事由/单号/报销人）过滤（推荐基线）。
2. 点击任一记录进入详情页，查看表头信息、全部费用明细、合计金额、状态与附件。

### J4 草稿整理、删除与已提交撤销（推荐基线）
1. 用户对「草稿」单据可继续编辑或删除；删除前需要二次确认。
2. 用户可对「已提交」单据执行「撤回」，单据回到「草稿」状态后可继续编辑（引用状态模型 T2）。

## 3. 状态模型与业务规则

### 3.1 状态定义
- 草稿：单据已创建但未正式提交，可编辑、可删除。
- 已提交：单据已完成正式提交，内容只读，等待后续业务处理（审核不在本基线范围，见第 6 节）。

### 3.2 状态转换
- T1：草稿 → 已提交。触发条件：用户对草稿执行「提交」且通过提交级校验（C5）。
- T2：已提交 → 草稿。触发条件：用户执行「撤回」（推荐基线）。
- 本基线不存在其他状态；状态仅能通过上述转换变化。

### 3.3 通用业务规则
- C1 唯一单号：每张报销单保存后由系统生成唯一报销单号，生成后不可修改、不可重复。推荐基线格式为「BX + 年月日 + 当日序号」（示例 BX20261015001），可按用户要求调整。
- C2 金额合计：合计报销金额 = 全部有效费用明细金额之和，由系统计算，用户不能手工改写合计值。
- C3 明细金额约束：单条明细金额必须大于 0，最多保留两位小数，不接受非数字输入。
- C4 表头必填约束：报销事由、报销人为必填；申请日期为必填且有默认值（当天，推荐基线）。其余表头字段为可选。
- C5 校验差异：「保存草稿」只校验表头必填项（C4），允许明细为空；「提交」额外要求至少存在一条合法费用明细。
- C6 只读约束：「已提交」单据不允许编辑、删除明细或调整表头，只能通过撤回（T2）回到草稿后再修改。
- C7 删除约束：仅「草稿」状态允许删除；删除必须经用户确认后才生效（推荐基线）。
- C8 防重复提交：对已处于「已提交」状态的单据再次触发提交不产生新单据（设计假设，保证结果一致性）。

## 4. 分模块功能需求

### FR-1 报销单列表与查询
- 行为：展示已创建的报销单，字段至少包含报销单号、报销事由、报销人、申请日期、合计金额、状态；默认按最近创建（或最后更新）时间靠前排布（设计假设）。提供进入「新建报销单」的入口（见 J1）和打开任一单据详情页的入口（见 J3）。
- 规则：支持按状态过滤；支持按关键字（事由/单号/报销人）检索（推荐基线）。列表数据应与实际持久化保存的单据一致。
- 边界与异常：无任何单据时显示空列表状态（设计假设）；过滤无结果时显示无匹配提示而不是报错。
- 禁止结果：列表中出现无单号或状态缺失的单据。
- 关联：J3、AC-01、AC-13。

### FR-2 新建与表头填写
- 行为：新建一张空白报销单，表头信息至少包含：报销单号（保存后由系统生成，创建阶段为空是正常状态）、报销事由（必填）、报销人（必填，手工输入，设计假设：本基线无账号体系）、申请日期（必填，默认当天，推荐基线）、备注（可选）、合计金额（系统计算展示，不可编辑，引用 C2）。
- 规则：报销事由输入长度设上限 200 字为推荐基线，超限给出可见反馈；字段以业务含义为准，具体界面布局由设计阶段决定。
- 边界与异常：必填项为空时不允许保存，提示具体缺失字段（引用 C4）。
- 禁止结果：保存后修改单号仍生效；用户手工改写合计金额。
- 关联：J1、AC-01、AC-02、AC-03。

### FR-3 费用明细维护与金额合计
- 行为：单据上可添加、修改、删除多条费用明细；每条明细包含费用日期、费用类别、用途说明、金额。费用类别推荐基线枚举：差旅费、招待费、办公费、交通费、通讯费、培训费、其他。
- 规则：明细金额遵守 C3；明细任何变更后合计金额按 C2 实时重算。费用类别默认可归入报销单整体用途，不强制与表头类别联动（设计假设）。
- 边界与异常：输入超过两位小数、零、负数或非数字时拒绝该明细写入并给出可见错误反馈；删除唯一一条明细后合计归零且允许保存为草稿（明细为空仅限制提交，不限制草稿保存，引用 C5）。
- 禁止结果：提交包含零或负金额明细的单据；合计与明细之和不一致。
- 关联：J2、AC-04、AC-05、AC-06、AC-07。

### FR-4 附件管理（推荐基线）
- 行为：单据级附件，可上传、查看清单、移除。附件用于留存发票或凭证图片。
- 规则：推荐基线支持常见图片格式与 PDF，单文件上限 10MB（均可调整）；附件为可选，不阻碍保存和提交。
- 边界与异常：超限或不支持类型的上传失败时给出可见错误反馈，不产生残缺附件记录；草稿保存后已上传附件应随单据保留。
- 禁止结果：附件上传失败却在单据上显示为已存在。
- 关联：AC-12。

### FR-5 保存草稿与提交校验
- 行为：提供「保存」和「提交」两个动作，输入内容一致但校验等级不同（引用 C5）。
- 规则：保存成功后生成唯一单号并按 C1 保持；提交成功后状态按 T1 变更并整体只读（C6）。提交失败时单据保持在原状态且内容不丢失。
- 边界与异常：草稿首次保存不强制明细；提交时明细为空提示「请至少填写一条费用明细」（推荐基线文案，可调整）。同一单据连续触发提交遵守 C8。
- 禁止结果：产生两张内容相同但单号不同、本应只提交一次的单据；保存成功却无任何单据可查。
- 关联：J1、J2、AC-02、AC-07、AC-08。

### FR-6 撤回、编辑与删除
- 行为：草稿可继续编辑并可删除；已提交单据可撤回回到草稿（T2，推荐基线）。
- 规则：编辑后重新走保存/提交流程，单号不变（C1）；删除遵守 C7。
- 边界与异常：对「已提交」单据直接发起编辑或删除请求必须被拒绝并给出可见提示（C6）；撤回后单据重新可编辑且历史记录仍为同一张单据（单号不变）。
- 禁止结果：删除「已提交」单据；撤回成功但单据仍不可编辑；编辑导致合计与明细不一致。
- 关联：J4、AC-09、AC-10、AC-11。

## 5. 非功能要求（可观察质量结果）

- N1 持久性结果：已保存的报销单（草稿与已提交）在页面刷新、关闭浏览器后重新打开时仍可完整读取，包括明细与附件内容。本条只约定结果，不推荐具体存储技术。
- N2 错误反馈：所有校验失败与操作拒绝都有用户可见的反馈，说明具体原因；不发生静默失败。
- N3 金额准确性：界面展示的合计与明细金额之和一致，按两位小数呈现。
- N4 设备范围：以桌面 Web 为目标；用户未提出移动端适配要求，不在本基线追加。
- 说明：用户未提出部署、性能指标、审计、国际化等要求，本基线不自行补齐；如后续提出再更新本文档。

## 6. 明确不在当前范围内的能力

依据：用户提出的业务任务限定为「创建费用报销单」。以下能力不属于该任务的字面范围，本基线不包含；如用户需要，应先补充确认再扩展需求：

## 7. 推荐基线与设计假设汇总

以下条目均为可安全推导的产品建议，非用户已确认事实，整体可调整：

- D-01 报销人无账号体系，作为表头字段手工输入（支撑 FR-2）。
- D-02 币种固定为人民币元（支撑 N3）。
- D-03 单号格式 BX+日期+当日序号（支撑 C1）。
- D-04 费用类别枚举表（支撑 FR-3）。
- D-05 附件类型与 10MB 上限（支撑 FR-4）。
- D-06 「已提交」单据允许撤回（支撑 T2、FR-6）。
- D-07 删除草稿需二次确认（支撑 C7）。
- D-08 申请日期默认当天（支撑 C4）。
- D-09 列表默认按时间倒序、支持状态过滤与关键字检索（支撑 FR-1）。
- D-10 报销事由长度上限 200 字（支撑 FR-2）。

## 8. 验收场景（AC）

### AC-01：从列表进入新建报销单
- 验收条件：报销单列表页存在「新建」入口，点击后打开空白报销单填写界面，申请日期默认带出当天。
- 入口类型：用户界面
- 前置条件：可访问费用报销单功能页面。
- 触发动作：在列表页点击「新建报销单」。
- 验证动作：打开创建界面并读取表头初始值。
- 预期结果：出现空白可编辑单据，申请日期显示为当天。
- 证据类型：runtime-render, interaction
- 共享流程组：创建与提交

### AC-02：保存草稿生成唯一单号
- 验收条件：填写报销事由、报销人后执行「保存」，单据保存成功、状态为「草稿」，并获得系统生成的唯一报销单号。
- 入口类型：用户界面
- 前置条件：已通过新建入口打开空白报销单。
- 触发动作：填写必填表头后点击「保存」。
- 验证动作：保存后读取单据信息与列表记录。
- 预期结果：提示保存成功，单据显示「草稿」状态和唯一单号；列表中出现该单据。
- 证据类型：interaction, runtime-render
- 共享流程组：创建与提交

### AC-03：表头必填项校验
- 验收条件：报销事由或报销人为空时执行保存或提交，系统拒绝并指明缺失的必填字段，内容不丢失。
- 入口类型：用户界面
- 触发动作：在必填表头为空时点击「保存」或「提交」。
- 验证动作：观察错误反馈与已填写内容。
- 预期结果：不发生保存；出现指向具体缺失字段的可见提示；已录入内容保留。
- 证据类型：error-feedback, interaction
- 共享流程组：必填校验

### AC-04：费用明细合计自动计算
- 验收条件：添加两条及以上费用明细后，合计金额等于各明细金额之和，并随明细增改实时刷新。
- 入口类型：用户界面
- 前置条件：处于可编辑报销单并有合法表头。
- 触发动作：依次添加两条金额不同的明细，再修改其中一条金额。
- 验证动作：读取每次操作后的合计显示并与手工求和比对。
- 预期结果：任一时刻合计与各明细之和一致（两位小数），修改后合计立即更新。
- 证据类型：runtime-render, interaction
- 共享流程组：创建与提交

### AC-05：明细金额非法输入反馈
- 验收条件：明细金额为 0、负数、非数字或超过两位小数时，系统拒绝写入并给出可见错误提示。
- 入口类型：用户界面
- 前置条件：处于可编辑报销单的费用明细区。
- 触发动作：分别尝试录入上述非法金额。
- 验证动作：观察每次非法录入的系统反馈。
- 预期结果：每条非法明细都不进入单据，合计不变，且每次都有具体原因提示。
- 证据类型：error-feedback, interaction
- 共享流程组：明细校验

### AC-06：删除明细后合计同步
- 验收条件：删除一条已有明细后，合计金额减少为其余明细之和。
- 入口类型：用户界面
- 前置条件：单据内已有至少两条合法明细。
- 触发动作：删除其中一条明细。
- 验证动作：读取删除后的合计。
- 预期结果：合计与剩余明细之和一致。
- 证据类型：interaction, runtime-render
- 共享流程组：创建与提交

### AC-07：无明细时不允许提交
- 验收条件：明细为空但表头完整时执行「提交」，系统拒绝提交并提示需至少一条费用明细；同一单据此时仍可直接保存为草稿。
- 入口类型：用户界面
- 前置条件：处于表头完整、明细为空的草稿。
- 触发动作：点击「提交」；再改点「保存」。
- 验证动作：观察提交的拒绝提示与随后保存的结果。
- 预期结果：提交失败且有具体提示；保存为草稿成功。
- 证据类型：error-feedback, interaction
- 共享流程组：明细校验

### AC-08：提交成功后状态变更且只读
- 验收条件：表头完整且至少一条合法明细的草稿执行「提交」后，状态变为「已提交」，单据转为不可编辑。
- 入口类型：用户界面
- 前置条件：已完成 AC-04 场景中的合法明细填写。
- 触发动作：点击「提交」。
- 验证动作：读取提交后的状态，并尝试修改任一字段。
- 预期结果：状态显示「已提交」，编辑入口不可用或修改被拒绝并有提示。
- 证据类型：interaction, runtime-render, error-feedback
- 共享流程组：创建与提交

### AC-09：已提交单据禁止直接编辑与删除
- 验收条件：对「已提交」单据发起编辑或删除操作均被系统拒绝，单据内容与状态保持不变。
- 入口类型：用户界面
- 前置条件：存在至少一张「已提交」单据。
- 触发动作：从列表/详情分别发起编辑与删除。
- 验证动作：观察系统反馈与单据数据。
- 预期结果：两类操作均被拒绝且提示原因；单据内容、状态、单号均不变。
- 证据类型：error-feedback, interaction
- 共享流程组：提交后生命周期

### AC-10：撤回后恢复可编辑
- 验收条件：「已提交」单据执行撤回后状态回到「草稿」，可以修改明细并重新保存、重新提交，单号不变。
- 入口类型：用户界面
- 前置条件：存在至少一张「已提交」单据。
- 触发动作：执行「撤回」，修改一条明细金额，再次「提交」。
- 验证动作：逐步读取状态、金额与单号。
- 预期结果：状态依次变为「草稿」→「已提交」，合计与新明细一致，单号保持原值。
- 证据类型：interaction, runtime-render
- 共享流程组：提交后生命周期

### AC-11：删除草稿需确认且生效
- 验收条件：删除「草稿」单据前系统要求确认；确认后单据从列表与查询结果中消失，未确认则删除不生效。
- 入口类型：用户界面
- 前置条件：存在至少一张「草稿」单据。
- 触发动作：先发起删除并取消确认；再次发起删除并确认。
- 验证动作：分别在两种确认后读取列表。
- 预期结果：取消时单据仍在；确认时单据不再显示且按单号查询无结果。
- 证据类型：interaction, error-feedback
- 共享流程组：提交后生命周期

### AC-12：附件上传、查看与失败反馈
- 验收条件：单据可上传受支持类型的附件并在详情中查看清单；对超出建议上限（10MB）或不支持类型的文件，上传失败给出可见错误提示且单据上不出现残缺记录。
- 入口类型：用户界面
- 前置条件：处于可编辑报销单。
- 触发动作：上传一个受支持文件，再尝试上传一个超限或不支持的文件。
- 验证动作：读取附件清单与失败提示。
- 预期结果：受支持文件出现在清单并可再次看到；失败上传有具体原因提示且不产生附件记录。
- 证据类型：interaction, error-feedback, runtime-render
- 共享流程组：附件管理

### AC-13：列表查询、过滤与详情查看
- 验收条件：列表按状态过滤和关键字检索时，结果与条件一致；打开任一单据详情页可见表头、全部明细行、合计金额与状态。
- 入口类型：用户界面
- 前置条件：至少存在一张草稿与一张已提交单据。
- 触发动作：按状态「已提交」过滤，再按某单号关键字检索并打开详情。
- 验证动作：比对过滤结果与详情页内容。
- 预期结果：过滤只含匹配记录；详情页内容与该单据保存数据一致。
- 证据类型：runtime-render, interaction
- 共享流程组：查询与持久化

### AC-14：刷新后数据持久可读
- 验收条件：已保存的草稿与已提交单据在刷新页面或重新打开应用后仍可查询，字段、明细与合计与保存时一致。
- 入口类型：用户界面
- 前置条件：已完成 AC-02 与 AC-08 的保存与提交。
- 触发动作：刷新页面（或关闭后重新打开）并查询该单号。
- 验证动作：读取列表与详情页数据并与提交前记录比对。
- 预期结果：单据完整可读，无字段或明细丢失。
- 证据类型：session-persistence, runtime-render
- 共享流程组：查询与持久化

## 9. 特殊工作台或特殊场景

本基线不涉及嵌入式页面、特殊运行工作台或外部系统集成。如用户后续提出（例如报销单需要嵌入其他系统页面），在此节补充再更新验收场景。
