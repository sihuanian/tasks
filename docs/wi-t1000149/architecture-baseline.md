## 1. 整体方案与设计基线

需求基线：`docs/wi-t1000149/requirements.md`（v1.0，sha256:c36754e9956ff91ac473fc5110728236c05ae68e7c524f35ab696f3286c29547）。本文只写技术承载与边界，不复述需求条款、用户旅程或验收场景。

应用形态结论：新建单体 Web 应用「费用报销单」。前端为 React + Vite 单页应用，后端为 Hono REST API 并以同一 Node 进程托管前端静态资源；数据由服务端权威 SQLite 持久化（分类为 fullstack-complex，依据批准快照 N1 持久性、FR-1 结构化查询、FR-4 附件随单据保留，需求未明示纯浏览器本地承载，歧义按分类合同走服务端）。本应用无认证、无授权、无外部系统集成（需求第 6 节明确排除），API 默认在本应用运行环境内公开可用；若未来部署到不可信网络，须先补认证再暴露，该演进不在本设计范围。

模块未覆盖部分（在项目内实现，不新增公共包）：报销单聚合（表头、明细、合计、状态机、单号生成）、按状态/关键字的列表查询、费用类别枚举与字段级校验。`authkit`/`userkit`/`permissionkit`/`auditkit` 未选择：需求无账号体系、角色权限与审计要求。附件的「分享链接/公开下载」为模块自带能力，本应用界面不接入该入口（超出需求）。

### 1.2 运行契约（冻结）

- 依赖安装 `npm install`；构建 `npm run build`（Vite 产物由 Hono 静态托管）；正式启动单进程：

startCommand: npm start

- 默认监听 `PORT=3000`（环境变量 `PORT` 可覆盖）；开发模式 `npm run dev`（vite dev server + Hono，前端经代理访问 `/api`）。
- 数据库文件：环境变量 `DB_PATH`，默认 `<packageRoot>/data/expense-reimbursement.db`；打开前自动创建父目录；服务只初始化所选路径，绝不重建或清空默认交付库。
- 附件目录：环境变量 `UPLOAD_DIR`，默认 `<packageRoot>/data/uploads`。
- 共享环境：`APP_URL`（默认 `http://localhost:3000`）、`JWT_SECRET`（附件 token 服务必填参数；本应用不接入分享功能，缺省时服务端使用内置开发值并仅在日志提示，不构成安全边界）。
- QA/验收：`node tests/verify.mjs`——脚本选择空闲端口、以隔离 `PORT`/`DB_PATH`/`UPLOAD_DIR`（临时目录）启动同一入口，等待真实监听就绪，验证业务结果并在 `finally` 清理自己启动的进程；不使用 `bash verify.sh`，不在验收中重跑 `npm start`。
- 运行时约束：Node >= 20（dbkit/attachment 清单要求），包管理器 npm（冷启动检查支持 Node/npm 并要求 package-lock.json）。

### 1.3 全局 UI 呈现基线

依据 ui-design-decision 参考与批准需求摘要一次性冻结：

- 应用类型与主用户工作方式：桌面 Web 业务后台；经办人以「单据列表 → 打开/新建记录 → 表单编辑 → 提交」的高频逐条工作方式为主。
- 应用/业务模板：无（需求不支持 helpdesk/看板/地图等工作方式，不套用）。
- 展示模板 ID：`split-master-detail`——核心动作为逐条处理报销记录（列表 + 当前记录表单/详情协同）；该 ID 同时是 Builder 读取实现资源的唯一标识。
- 主工作流布局：主工作区左列为报销单列表（含状态过滤、关键字检索、「新建报销单」入口），右区为当前单据的编辑表单或只读详情；表单内自上而下为表头信息区、费用明细行编辑区（实时合计展示）、附件区、底部动作区（保存/提交/撤回/删除）。已提交单据右区呈只读态并提供撤回入口。
- 视觉风格：默认 Modern SaaS——柔和中性色、细边界、少阴影、中等圆角、清晰字体层级；单一主色 + 状态色区分「草稿/已提交」；动效短促且仅用于反馈（保存成功、校验错误抖动/高亮一类）。不引入装饰性 3D、大面积渐变或低信息密度卡片墙。
- 应用壳与导航：左侧固定导航（单一功能入口「费用报销单」）+ 顶部上下文栏（应用名、当前单据单号）；不增设仪表盘或首页。
- 设备策略：桌面 Web（沿用需求 N4），不设计移动端/窄屏，不追加窄屏表格策略。
- 全局状态策略：加载（骨架/进度占位）、空数据（列表为空的新建引导）、无匹配（过滤/检索无结果的提示而非报错）、错误（表单字段级与服务操作级可见反馈，含附件上传失败）、成功（保存/提交/撤回轻提示）。无权限状态不适用（本应用无权限体系）。
- 图标：使用 Lucide 图标库保持单一图标家族；不以 emoji 充当功能图标。

模块级页面细节（字段布局、控件选择）由实现阶段在全局基线内决定；Builder 不得替换全局展示模板与视觉风格。

## 2. 领域责任、模块边界与接口摘要

调用方向（单一服务端边界）：

```text
浏览器 React SPA ──HTTP/JSON──▶ Hono API（含静态托管）
                                   │
                                   ├─▶ 报销单 Service ─▶ Repository ─▶ dbkit ─▶ SQLite
                                   │        （表头/明细/合计/状态机/单号的唯一 owner）
                                   └─▶ @commonapp/attachment 路由
                                            ├─▶ AttachmentRepository ─▶ dbkit ─▶ SQLite（attachments 表）
                                            └─▶ LocalStorage ─▶ UPLOAD_DIR 磁盘文件
```

- 报销单领域服务（项目内，唯一事实归属）：报销单表头、费用明细、合计金额（服务端权威重算）、状态机（草稿/已提交，T1/T2 转换与只读/删除约束）、唯一单号生成（保存事务内日期序列）全部由此模块唯一拥有；校验规则 C1–C8 的服务端落点在此。
- 附件集成（复用模块）：附件文件与记录的 owner 是 `@commonapp/attachment`（元数据存 SQLite、文件存磁盘），宿主只提供挂载配置与 hooks：`canAccess` 按单据状态约束（草稿可上传/移除，任何状态可查看下载，单据不存在拒绝），`resolveUser` 映射固定匿名身份（无账号体系）。上传失败不产生残缺记录是模块验证清单要求的行为边界。
- API 层：Hono 路由，请求解析与面向前端的错误模型；字段级契约的唯一来源是 `technical-contract.md`（接口路径、模型、校验、错误、幂等），本文只保留摘要引用。
- Web 客户端（React SPA）：列表视图、编辑/详情视图、明细行编辑与本地实时合计预览；不持有跨会话状态，页面数据全部来自 API。附件区直接消费模块组件与 API client。
- 模块间只通过公开 Service/路由调用，前端不读取数据库、服务端不因附件改变报销单状态。

## 3. 数据与迁移

逻辑数据模型（物理 DDL 以 `migrations/sqlite/` 版本化 SQL 为准，dbkit `runMigrations` 执行；本应用无既有数据，不存在迁移回填）：

- `expense`（报销单聚合根，owner：报销单 Service）：内部主键 id、唯一单号 number、表头字段（报销事由、报销人、申请日期、备注）、状态枚举（draft/submitted）、服务端合计 total_amount_cents、创建/更新时间。单号唯一性由 UNIQUE 约束兜底。
- `expense_item`（明细行）：外键指向 expense，随单据级联删除；费用日期、费用类别（七值枚举）、用途说明、金额（整数分存储，两位小数精度，>0）。
- `expense_number_seq`（内部序列表）：按日期累计当日序号，支撑单号 C1 的并发唯一；与单据插入同事务写入。
- `attachments`（owner：attachment 模块）：由 `getAttachmentDdl` 生成的表，`entityColumn=expense_id` 关联报销单；其 DDL 作为宿主版本化迁移提交，不在启动时重复建表。

金额约定：一律「分」整数落库，接口层为两位小数数值；合计恒等于明细金额之和（C2/N3 的服务端保证），前端实时求和仅作显示预览，保存/提交后以服务端返回值为准。删除唯一明细后合计归零但草稿仍可保存的行为由「明细为空不阻断保存、仅阻断提交」的校验等差实现（C5）。

## 4. 外部集成与失败处理

无外部服务集成（需求第 6 节明确排除 ERP/OCR/第三方）。唯一的对外持久化副作用是附件文件写入本地磁盘：容量超限、类型不符等失败必须返回可见错误且不留下记录或残缺文件（模块行为边界）；SQLite 写失败通过事务回滚保证单据与明细不出现半成品状态。错误对用户的呈现统一为字段级/操作级可见反馈（N2）。

## 5. 关键决策

- AD-1 服务端权威存储取代浏览器本地：N1「刷新/重开后完整可读」+ FR-1 结构化检索 + 附件随单据保留，且需求未声明纯单浏览器本地使用；采用 dbkit/SQLite，数据归属集中于服务端。若用户后续确认只要单设备本地版，可降级为纯前端方案（影响：单号并发保证与查询能力实现方式整体更换）。
- AD-2 复用 @commonapp/attachment 而非自研上传：FR-4/D-05 与模块能力（10MB 默认上限、上传/清单/删除、React 组件）高度匹配；代价是引入 JWT_SECRET/APP_URL 配置（仅作模块必填参数，本应用不开放分享）并以无认证 hooks 适配——canAccess 只按单据状态判定。
- AD-3 整单替保存模型：编辑一次「保存」提交表头+全部明细，服务端在事务内替换明细行并重算合计；实现与前端表单化编辑一致，保证 C2/N3「合计永远与明细一致」不依赖多次散落写请求的顺序。
- AD-4 状态操作显式化：提交/撤回/删除是独立端点而非字段改写，服务端以「当前状态」为条件做原子转换，非法转换（含已提交单据再提交）一律拒绝且幂等（C6/C8），单号在撤回重提交全程不变（C1）。

## 6. 边界与未决项

- 需求分类 unresolved 项（跨设备/跨用户共享）按服务端方案已天然覆盖，不阻塞实现。
- 明确不做：审核流、付款记账、账号与权限、多币种、外部集成（需求第 6 节）。
- 列表不做分页：需求无分页/性能指标；如数据量增长需要分页，属需求变更而非本设计范围。
